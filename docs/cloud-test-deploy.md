# 인터넷 주소 + 폰 앱(사용성 테스트) — 2026-10-22 형우 확정

## 결정
- 목적: 사내 서버로 옮기기 전에 인터넷 주소로 열어 보고 폰에서 앱처럼 써 보며 사용성 확인.
- 방식: 클라우드, 무료, 카드 없이 → GitHub(비공개 코드, nogotheater/gitsn) + Render(실행, 싱가포르, 무료) + Supabase(DB·로고, 싱가포르, 무료).
  - 오라클 무료 서버는 검토 후 제외(형우). Cloudflare Pages·GitHub Pages는 Python 서버를 못 돌리고 무료 공개라 제외.
- 실제 고객 데이터를 올림(형우 결정 — 이번부터 PC 밖으로 나감). GitHub에는 코드만, 자료는 Supabase에만.
- 폰 앱: 웹 앱(PWA). 주소를 열고 '홈 화면에 추가' → 아이콘·전체 화면. 앱스토어 없음.
- 주소: https://gitsn.onrender.com (이름이 이미 있으면 Render가 뒤에 글자를 붙임). 회사 도메인은 사내 서버로 갈 때.

## 보호
- 모든 화면 로그인(PC 계정 그대로 — DB를 옮김), https만, DEBUG 끔.
- Supabase: public 스키마 표의 anon·authenticated 권한 회수 + 행 보안(RLS) 켜기(정책 없음) → Supabase 웹 API로는 못 읽음. 로고는 비공개 버킷(logos), 화면에는 로그인한 사람에게만 서버가 내려줌.
- 비밀 값(DB 비밀번호·저장소 키)은 저장소에 없음 — Render 화면과 PC의 _cloud\supabase.txt에만.
- 서비스 워커는 고객 자료를 폰에 저장하지 않음(끊기면 안내 화면만).

## 무료라서 생기는 것
- Render: 15분 안 쓰면 잠듦, 다시 열 때 1분쯤. 메모리 512MB라 PDF 만들기는 시험 필요.
- Supabase: DB 500MB, 일주일 안 쓰면 일시정지(화면에서 재개).

## 구성
- render.yaml(Render 설정), scripts/start_prod.py(gunicorn), config/settings.py(서버 환경에서만: Render 주소, 프록시 https, WhiteNoise, Supabase 암호화 연결, S3 저장소).
- scripts/supabase_restore.sh(PC DB → Supabase, 처음 한 번), scripts/upload_media.py(로고 → Supabase 저장소).
- PC 쪽: _map_tasks/160(검사·기록·GitHub 올리기), 161(PC 자료 → Supabase).

## 속도 보완 (2026-10-22, 형우 "너무 느리다")
- 측정: 로그인 전 화면은 0.13초 안팎으로 빠름 → 느린 곳은 로그인 후 화면(고객사 504곳·로고 요청·DB 왕복)과 잠든 서버 깨우기.
- 코드: 로고 파일을 서버 메모리에 보관(권한 확인은 매번, 브라우저 no-store 정책 그대로), DB 연결 60초 재사용(서버에서만), gunicorn 스레드 4개(로고·DB 기다리는 동안 다른 요청 처리).
- 잠듦: 15분 무사용 시 잠듦 → 외부 무료 알림 서비스(cron-job.org 등)로 10분마다 /health/live/ 를 불러 깨워 두기(형우 선택).
- 근본: 무료 서버 CPU 0.1개. 더 빨라야 하면 Render 유료(월 7달러, CPU 0.5·잠듦 없음) 또는 사내 서버.
- 2차(형우: 인쇄 미리보기·로고·지역 현황이 느림): 인쇄 미리보기가 글꼴 파일(7MB)을 페이지 안에 통째로 넣어 매번 9MB를 받고 있었음 → 미리보기는 글꼴을 주소로 받아 브라우저가 다시 씀(PDF는 그대로 넣음). 인쇄용 로고 줄이기 결과·글꼴 읽기 결과를 서버 메모리에 재사용. 지역 현황 계산 결과를 자료가 바뀌기 전까지 재사용(서버에서만).
- 3차 측정(로그인해서 직접): 납품현황 서버 1.0초 + 로고 하나에 0.7~1.2초(요청마다 로그인 확인·DB 조회) → 로고 다 뜨는 데 5초쯤. 인쇄 미리보기 서버 1.0초 + 화면 쪽 나누기 2.5초(PC). 지역 현황 0.9초(재사용 효과). 로그인 직후 첫 화면 4초는 비밀번호 확인 계산(일부러 느린 보안 계산)이 0.1코어에서 도는 것. CSS·JS를 화면마다 다시 확인(한 번에 0.15~0.45초).
- 3차 보완: 주소에 ?v=가 붙은 CSS·JS는 30일 보관. 직원이 보는 로고는 그 기기에 1시간 보관(파트너사는 기존대로 저장 안 함 — 공개 정책 즉시 반영). 서버가 쓴 시간을 응답 머리(Server-Timing)에 적어 다음 측정에 씀.

## 속도 4차 (2026-10-22, 형우: "중앙정부 눌렀다가 공공기관 누르면 1~2초 뒤에 바뀐다")
- 분류 칩: 같은 제품·검색 조건의 전체 목록을 브라우저가 한 벌 들고 있다가, 누르는 순간 그 안에서 고른 분류만 남긴다(서버 응답을 기다리지 않음). 링크·숨은 칸 등은 뒤에서 서버 응답으로 조용히 맞춘다. 분류를 고른 화면으로 바로 들어오면 전체 목록을 뒤에서 한 번 미리 받아 둔다. 미리 받기 전이거나 결과가 빈 화면이면 예전 방식(서버에서 받아 바꿈).
- 목록 그리기: 카드 include를 목록 안에 바로 쓰고, 카드 주소·로고 주소·마킹 색은 화면 코드에서 한 번에 만든다(카드마다 주소 계산 안 함).
- 검사: test_category_chip_switches_list_at_once_then_matches_server (클릭 직후 목록·주소·총수가 이미 바뀌고, 뒤에서 맞춘 링크가 서버가 새로 그린 것과 같다).

## 속도 5차 (2026-10-22, 형우: "제품 필터 누르고 나오는 시간도 딜레이")
- 제품 칩·분류 칩·조건 해제 칩·모두 해제: 아무것도 안 고른 전체 목록과 집계표(`#count-index`)를 브라우저가 들고 있다가, 누르는 순간 고른 제품(하나 이상 도입)·분류로 카드를 남기고 숫자(총수·분류 칸·섹션·비공개 포함 수)를 다시 센다. 마킹 강조·흐림과 순서도 서버와 같게 바꾼다.
- 집계표에는 이름·로고·주소가 없다: 숫자에 들어가는 고객사마다 (분류, 권역, 공개 여부, 제품) 뿐. 파트너도 칩을 눌러 얻을 수 있는 숫자와 같은 정보다.
- 검색어가 바뀌면(검색·검색 지우기) 예전처럼 서버에서 받는다. 그 검색어의 전체 목록은 뒤에서 받아 둔다.
- 검사: test_product_and_category_chips_redraw_at_once_exactly_like_server — 직원·파트너 각각, 칩 6번을 눌러 그 순간의 화면이 새로고침한 서버 화면과 똑같은지 비교.
