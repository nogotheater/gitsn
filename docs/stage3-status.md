# 3단계 기획팀 등록·수정 화면
기준일: 2026-10-16. 상태: 사용자 PC 전체 검사에서 오류 9개 확인, 검사 코드 수정 후 실제 PostgreSQL·Chromium 재검증 대기.
사용자가 3단계 진행을 요청했다. 재시작 보존 등 이전 환경 검증의 남은 항목은 유지한다.

## 반영한 내용
- 고객사 검색·신규 등록·수정, 계약별 제품·전체 수량·장소별 실제 제품 입력, 계약 수정·종료 확인, 장소 표시 설정, 기획팀용 제품 목록 추가·표시 수정.
- 기획팀 관리 권한을 화면과 저장 서비스 양쪽에서 검사한다. 이 단계에서 화면을 쓰기 위한 최소 로그인·POST 로그아웃만 연결했다. 직원/파트너사 현황 화면과 계정 관리 화면은 4단계다.
- 입력 실패 시 글자·선택·수량·장소 입력을 같은 화면에 유지한다. 브라우저 파일 입력은 보안상 다시 선택해야 할 수 있음을 안내한다.
- PNG/JPG(확장자 jpg/jpeg/png), 2MB 이하로 사용자 확정. 2MB는 2,097,152바이트다. 실제 이미지 형식을 검증하고 파일명은 무작위로 저장한다. 심볼이 없으면 명칭 첫 글자로 기본 표시한다.
- 로고는 기획팀 권한을 확인한 주소로만 제공한다. media 폴더를 공개 주소로 연결하지 않았다. 일반 직원/파트너사에 대한 로고 전달은 4단계에서 권한 범위를 연결한다.
- ‘표시 구분’을 독립된 display_as 필드로 추가했다. 기존 고객사는 customer, 기존 장소 표시 기록은 site로 초기화하는 0004 변경 파일이다. 이 값은 고객사 수 포함 여부·목록 노출·공개 여부와 독립적이다. 내부 식별 종류 kind를 바꾸거나 기록을 자동 통합하지 않는다.
- 같은 공식 명칭의 고객사 신규 등록은 기존 자료를 선택하도록 안내하며 자동으로 합치지 않는다. 다른 표기·동명이인·수동 통합은 이후 범위다.
- 새 장소 명칭이 기존 장소와 같아도 자동 연결하지 않는다. 기존 장소를 직접 선택해야 재사용한다. 재사용 장소의 표시 설정은 ‘기존 장소의 표시 설정도 변경’을 선택한 때만 바뀐다. 연결된 다른 계약에도 적용됨을 안내한다.
- 저장은 DB 트랜잭션으로 처리한다. 계약·제품·장소 저장 중 실패하면 모두 취소한다. 수정 시 최근 수정일을 비교해 오래된 화면이 새 내용을 덮어쓰지 않게 한다.
- 종료는 확인 화면의 POST로 처리하며 과거 기록을 보존한다. 일부 계약 종료 후 남은 유효 수량만 반영하고, 유효 계약이 모두 끝나면 현재 목록·집계에서 제외한다.
- 분류 변경 시 공개값을 새 분류 기본값으로 초기화한다. 신규 등록과 분류를 바꾸지 않는 수정에서는 기획팀의 개별 공개 선택이 가능하다.

## 디자인
확정된 design-system.html을 직접 확인했다. Freesentation VF 원본 글꼴을 추출해 같은 서버에서 제공하며 폰트를 교체하지 않았다. 브랜드 색 #1A8CF7, 동작 색 #0474D4, 회색·간격·모서리·컨트롤 높이·반응형 기준을 적용했다. 관리 목록은 큰 화면 카드·작은 화면 목록이다. 고정된 목록 24개 단위와 이름순 정렬은 관리 화면 구현 기본값이며 영업 현황 화면의 최종 검색·정렬 정책을 확정한 뜻은 아니다.
계약 입력을 위한 제품 관리에서 이름·코드·기호·색상을 등록할 수 있다. Alpha-C/C와 Alpha-I/I만 최초 로컬 계정 준비 시 생성하며 확정되지 않은 제품 색상은 저장하지 않는다. 색상 미입력 시 기본 회색 마킹을 사용한다.

## 검증 결과
- Django 시스템 검사 통과, 모든 템플릿 구문·Python 구문 검사 통과. 실제 DB에 쓰지 않는 검토용 자료로 8개 화면 양식을 렌더링했다. 브라우저에서의 시각 검토·조작 완료를 뜻하지는 않는다.
- DB를 사용하지 않는 기존 업무·공개 범위·새 입력 사례 35개 통과.
- PostgreSQL 분리 테스트 DB에서 실행할 HTTP/저장 사례 18개와 Chromium 조작 사례 1개를 작성했다. 계정·고객사 자료는 실제 로컬 고객 DB에 등록하지 않는다.
- 실제 DB와 Chromium은 작성 환경에서 실행할 수 없으므로 54개 전체 검증 통과로 표시하지 않는다. 사용자 PC에서 STAGE3_FORMS_CHECKS_OK를 확인해야 한다.
- 브라우저 사례: 로그인 → 고객사 등록 → C 10대/I 5대 계약과 실제 C 설치 장소 저장 → 합계 15대 → 375px 모바일 가로 넘침 확인 → 수정 화면 → 로그아웃 → 재로그인 후 저장 자료 재조회. Freesentation VF 로드도 확인한다.
- HTTP 사례: 기획팀만 접근·저장, CSRF, 잘못된 수량·중복 제품·장소 제품 불일치·지자체 지역 필수, 오류 시 입력 보존·전체 저장 취소, 일부/전체 종료와 과거 수량 보존, 오래된 수정 거부, 심볼 보호, 로그인 권한·외부 이동 거부, 이름 이스케이프.

## PC 적용 순서
1. GITSN_stage3_update.py를 manage.py가 있는 폴더에 둔다.
2. Docker DB가 실행 중인 상태에서 해당 폴더 PowerShell에서 실행한다.

```powershell
docker compose run --rm --no-deps -T --user 0 --volume "$($PWD.Path):/app" web python GITSN_stage3_update.py
```

기존 소스 버전과 변경 여부를 먼저 확인한다. .env·기존 비밀번호·Docker 볼륨을 덮어쓰거나 삭제하지 않는다. 변경 파일 0004를 적용한 뒤 임의 이름의 별도 테스트 DB에서 전체 검증을 실행하고 없앤다. 테스트가 실패하면 성공으로 표시하지 않는다.
3. STAGE3_FORMS_CHECKS_OK와 STAGE3_UPDATE_AND_CHECKS_OK를 확인한 뒤 실행 중 웹을 새 코드로 구성한다.

```powershell
docker compose up -d --build --wait --wait-timeout 180
```

4. 최초 로컬 기획팀 계정을 직접 만든다.

```powershell
docker compose exec web python scripts/bootstrap_manager.py
```

아이디와 비밀번호를 직접 입력한다. 비밀번호 입력은 화면에 나타나지 않는다. 이 도구는 기존 계정 비밀번호를 바꾸지 않으며 고객사·계약을 만들지 않는다. 이후 http://localhost:8000 에서 로그인한다.

- 분류 전체 강제 비공개 정책과 개별 설정 충돌, 상세 지역 대응표(제주 등), 다른 명칭 관리·특수 중복 통합은 [확인 필요]. 현재는 저장된 개별 공개값과 명시적으로 선택한 고객사/장소 관계로 동작한다.
- 이전 단계의 재시작 후 DB/미디어 보존 검증과 마이그레이션 재적용 기록은 남아 있다. 이번 사용자 PC 적용·실행 결과와 별도로 기록한다.
- 실제 배포·다른 기기 접속 설정은 하지 않았다. 현재 로컬 주소에서 확인한다.

## 사용자 PC 검사 오류와 수정 — 2026-10-16 09:13 KST
- 사용자 제공 stage3-result.txt에서 PostgreSQL 변경 파일 0001~0004 및 세션 변경 적용 성공, 전체 54개 실행 중 오류 9개를 확인했다. 실제 전체 검증은 실패했으며 완료로 표시하지 않는다.
- 첫 오류는 로고의 FileResponse를 TestCase에서 response.close()로 직접 닫아 현재 테스트 트랜잭션의 PostgreSQL 연결까지 종료한 것이다. 이후 7개 검사는 같은 연결 오류로 시작 단계에서 실패했다. 테스트 클라이언트가 감싼 streaming_content를 끝까지 읽어 정상 정리하도록 바꿨고, PNG 서명·응답 닫힘·후속 DB 조회도 확인한다. 실제 로고 제공·저장 서비스는 바꾸지 않았다.
- 브라우저 검사는 정확한 href=/planning/customers/new/를 찾았으나 실제 링크는 검색어를 넘기는 ?name=를 포함한다. 화면의 ‘＋ 고객사 등록’ 링크 이름으로 찾도록 변경했다. 버튼이나 제품 기능은 바꾸지 않았다.
- 변경 후 DB 비의존 35개 검사와 Python 구문 검사를 통과했다. DB 연결 정리 신호의 차이를 모형으로 재현하고, 실제 템플릿을 렌더링해 새 링크 이름이 하나에 대응함을 확인했다. 이는 PostgreSQL·Chromium 전체 통과를 대신하지 않는다.
- 업데이트 도구는 이전에 제공한 3단계 파일의 확인된 해시도 허용한다. 따라서 이미 적용한 뒤 검사에 실패한 PC에서도 새 파일을 재실행할 수 있다. 임의로 편집한 파일은 계속 거부하며 .env·기존 로고·실제 고객 자료를 덮어쓰지 않는다.
- 수정된 전체 54개 검사 결과는 사용자 PC에서 다시 확인해야 한다. 오류를 건너뛰거나 검사를 비활성화하지 않았다.
