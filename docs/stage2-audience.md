# 2단계 직원·파트너사 공통 조회

## 구현 범위
- current_performance_payload(request.user, ...)가 실제 로그인 이용자의 직원/파트너사 구분을 확인한다. 화면에서 전달한 audience 값으로 권한을 결정하지 않는다.
- 로그인하지 않은 이용자, 비활성 계정, 직원/파트너사 설정이 없는 계정은 거부한다. Django 요청마다 확인된 사용자 객체를 사용하고 사용자 객체나 응답을 권한 간에 공유 캐시하지 않는다.
- require_employee는 직원용 상세 진입에, require_manager는 직원 중 delivery.manage_delivery 권한이 있는 기획팀의 수정·계정 관리 진입에 사용한다. 파트너사에 관리 권한을 잘못 부여해도 직원/관리자로 전환되지 않는다.
- contract_source_metadata는 기획팀 관리 권한을 확인한 뒤 메일 출처 정보만 반환한다. 일반 직원과 파트너사는 거부한다.
- 유효 계약·제품 복수 선택 모두 일치·분류·지역 조건을 적용한 동일 후보에서 목록과 집계를 각각 계산한다. 비공개와 목록 미표시 항목을 총수에서 자동 제외하지 않는다.
- 파트너사 목록에 표시할 공개 항목만 이름·제품·로고 유무를 조회한다. 비공개 고객사의 명칭, 식별값, 파일 경로, 개별 제품, 수량, 메모, 계약·메일 정보는 파트너사 반환 자료에 없다.
- 목록은 허용된 항목만 새 사전으로 구성한다. 계약 수량과 메일 출처는 직원 목록에도 포함하지 않는다. 실제 로고 경로를 반환하지 않으며 보호된 로고 전달 경로는 4단계에 구현해야 한다.
- 제품·분류·지역 조건이 맞지 않으면 목록은 비고 집계는 0이다. 잘못된 분류·지역·제품 식별 형식은 거부한다. 제품 식별값이 올바르지만 존재하지 않으면 결과 0이다.
- 분류 전체 강제 비공개 기능은 이번에 추가하지 않았다. 현재는 저장된 개별 공개값으로 판단한다. 분류 기본값과 분류 변경 시 초기화는 기존 확정 규칙을 따른다. 강제 비공개와 개별 설정 충돌 정책은 미정이다.

## 검증
- DB 비의존 검증 30개 통과. 이 중 공개/비공개 투영·접근 경계 사례 9개를 추가했다.
- 공개 70·비공개 30에서 직원/파트너사 총수 100 일치, 비공개 이름·개별 제품의 반환 자료 부재, 집계/표시 독립, 비로그인·비활성·미설정 계정 거부, 일반 직원/파트너사 출처 거부를 확인했다.
- 새로운 고객사·장소 제품 조회의 SQL 구문 생성은 확인했다. 실제 PostgreSQL 통합은 사용자 PC에서 scripts/verify_stage2_access.py로 확인할 예정이다. 아직 통과로 표시하지 않는다.
- 실제 PostgreSQL 진단은 기존 고객사·표시 장소를 등록하기 전에 실행한다. 가상 고객사 100곳과 임시 직원/파트너/기획팀 계정을 한 트랜잭션 안에 만든 뒤 모두 롤백한다. 임시 계정은 로그인할 수 없는 비밀번호를 사용한다. 기존 고객 자료가 있으면 생성 전에 중단한다.

## 이후 단계에서 확인할 사항
이번 작업은 공통 서비스이며 로그인·등록·상세 화면, HTTP 주소 접근 제어, 보호된 로고 경로, 인쇄·PDF 연결을 완성한 것이 아니다. 각 화면은 위 공통 서비스와 권한 검사를 재사용하고 주소 직접 입력·HTML·PDF 결과에 대한 검증을 별도로 수행해야 한다.
마이그레이션 재적용, 재시작 후 DB/미디어 보존, Chromium PDF 실행도 별도 미완료 사항이다. 3단계 화면은 이번 작업에 포함하지 않았다.
